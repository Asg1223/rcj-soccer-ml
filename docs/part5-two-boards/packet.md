# 5-2 パケットを設計する

## ねらい

- バイトの流れから「1 つのまとまり（パケット）」を正しく切り出す仕組みがわかる
- 先頭の印・長さ・チェックサム（CRC）の役割を説明できる
- C と Python で同じパケットを作り・読み、壊れたパケットを見つけられる

---

## 理論 1：なぜ「文字の行」ではだめなのか

1-3 では、`IR,1538,412,...` のような **文字の行** を送りました。人が読めて便利ですが、

- 数字 1 つに最大 5 バイト（`1023,`）使うので、量が多い
- 途中の 1 バイトが化けても、数字として読めてしまうことがある（`412` → `452`）

という弱点があります。マイコン同士なら、人が読めなくてよいので、**バイナリ** で送ります。

## 理論 2：パケットの形

この教材のパケットは、次の形にします。

| 位置 | 名前 | 大きさ | 中身 |
|---|---|---|---|
| 0, 1 | 先頭の印 | 2 バイト | いつも `0xA5 0x5A` |
| 2 | 種類（TYPE） | 1 バイト | `0x01` センサの値、`0x02` ボールの推定、`0x10` モータ |
| 3 | 長さ（LEN） | 1 バイト | 中身のバイト数（最大 64） |
| 4 | 番号（SEQ） | 1 バイト | 送るたびに 1 ずつ増える。抜けがわかる |
| 5〜 | 中身（PAYLOAD） | LEN バイト | センサの値 12 個なら 24 バイト |
| 最後 | CRC | 1 バイト | 種類から中身の最後までから計算したチェックの数 |

それぞれの役割はこうです。

- **先頭の印**：途中から受け取りはじめても、印を探せば区切りがわかる
- **長さ**：どこまでが中身かがわかる。長すぎる値なら「壊れている」と判断できる
- **番号**：パケットが抜けたこと（取りこぼし）がわかる
- **CRC**：中身が 1 ビットでも変わっていたら、ほぼ確実に気づける

## 理論 3：CRC とは

**CRC**（巡回冗長検査）は、データから決まった計算で作る「指紋」のような数です。送る側がデータと一緒に CRC を送り、受け取る側も同じ計算をして、**一致しなければ壊れている** と判断します。

単純に全部のバイトを足す「チェックサム」だと、2 つのバイトが入れかわっても同じ値になってしまいますが、CRC はそういう壊れ方にも気づけます。この教材では、多項式 `0x07` の **CRC-8** を使います。

## 手を動かす 1：Python でパケットを作る

```python
from rcjml.packet import encode, Parser, pack_ir, unpack_ir, pack_ball, unpack_ball, crc8, T_IR_RAW, T_BALL

values = [650, 420, 80, 0, 0, 0, 0, 0, 0, 0, 51, 430]
pkt = encode(T_IR_RAW, seq=7, payload=pack_ir(values))
print(len(pkt), "バイト:", pkt.hex(" "))
```

先頭が `a5 5a`、次が種類 `01`、長さ `18`（16 進数で 24）、番号 `07`、そのあと 24 バイトの中身、最後に CRC です。文字の行（約 50 バイト）より小さくなりました。

## 手を動かす 2：受け取る側（パーサ）

受け取る側は、バイトを 1 つずつ見て、

1. `0xA5` を待つ → 2. 次が `0x5A` か → 3. 種類・長さ・番号・中身を集める → 4. CRC を確かめる

という順に進みます（**状態機械** といいます）。

```python
parser = Parser()
print(parser.feed(pkt))                 # 1 つそろった
print(unpack_ir(parser.feed(pkt)[0].payload))
```

## 手を動かす 3：わざと壊して確かめる

本番の通信では、モータのノイズなどでバイトが化けたり、途中から受け取りはじめたりします。それでも正しく動くかを試します。

```python
import random
rnd = random.Random(0)
stream = bytearray()
expected = 0
for k in range(200):
    vals = [rnd.randint(0, 1023) for _ in range(12)]
    p = bytearray(encode(T_IR_RAW, k, pack_ir(vals)))
    if k % 10 == 3:
        p[7] ^= 0x40                    # 10 回に 1 回、中身を 1 ビット壊す
    else:
        expected += 1
    stream += bytes(rnd.randint(0, 255) for _ in range(rnd.randint(0, 3)))   # ゴミのバイト
    stream += p

parser = Parser()
got = parser.feed(bytes(stream[5:]))    # 途中から受け取りはじめる
print(f"正しく受け取れた {parser.ok}（壊していないのは {expected}）, CRC で見つけた {parser.crc_errors}")
```

壊したパケットは CRC ではじかれ、ゴミのバイトがあっても、途中から受け取りはじめても、次の先頭の印から正しく読めます（最初の 1 つは途中から読むので取れません）。

## 手を動かす 4：C 版と同じか確かめる

マイコンで使うのは、`firmware/common/rcjml_packet.h` の C 版です。教材では、C 版で作ったパケットを Python で読む、Python で作った（壊したものも含む）パケットを C 版で読む、の両方を gcc で確かめ、**同じ結果** になることを確認しています。

C 版の使い方はこうです。

```c
#include "rcjml_packet.h"

// 送る
uint8_t payload[24], buf[6 + 24];
for (int i = 0; i < 12; i++) rcjml_put_u16(payload + 2 * i, values[i]);
uint16_t n = rcjml_pkt_encode(RCJML_T_IR_RAW, seq++, payload, 24, buf);
Serial2.write(buf, n);

// 受け取る
rcjml_parser_t parser;          // setup() で rcjml_parser_init(&parser);
while (Serial2.available()) {
  if (rcjml_parser_feed(&parser, Serial2.read())) {
    // parser.type, parser.len, parser.payload が使える
  }
}
```

!!! tip "スケッチのフォルダにヘッダをコピーする"
    Arduino IDE は、スケッチのフォルダの外にあるヘッダを読めません。使うスケッチのフォルダに、ターミナルで次のようにコピーします。

    ```bash
    python -m rcjml.export headers firmware/sensor-arduino/ir_ring_uart
    ```

## チェック問題

1. 受け取りはじめたとき、ちょうどパケットの真ん中でした。この仕組みでは、どうやって次のパケットの始まりを見つけますか。
2. 番号（SEQ）が 41, 42, 44, 45 と届きました。何が起きましたか。
3. 長さ（LEN）が 200 と届きました。どうしますか。

??? note "答え"
    1. 先頭の印 `0xA5 0x5A` が来るまで読み捨てます。中身にたまたま同じ並びがあっても、長さと CRC が合わないので、はじかれます。
    2. 43 番のパケットが届かなかった（取りこぼした、または CRC ではじいた）ことがわかります。
    3. 最大の 64 を超えているので、壊れていると判断して捨て、また先頭の印を探します。

## つまずきポイント

??? failure "CRC エラーがとても多い"
    - 速さ（ボーレート）が送る側と受け取る側で違う
    - GND がつながっていない
    - 線が長い・モータの線と並んでいてノイズを拾っている

    の順に確かめます。速さを 115200 から 57600 に下げると改善することもあります。

??? failure "まったく受け取れない"
    TX と RX が逆になっていないか確かめます（自分の TX は相手の RX）。

## もっと深く

!!! deeper "バイトの並び順（エンディアン）"
    2 バイトの数 1023（16 進数で `0x03FF`）を送るとき、`FF 03` の順（下位が先：**リトルエンディアン**）と、`03 FF` の順（上位が先：**ビッグエンディアン**）があります。この教材はリトルエンディアンにそろえています。ESP32 も Arduino も PC もリトルエンディアンなので、ずれる心配は少ないですが、違う種類のコンピュータとやりとりするときは、必ず決めておく必要があります。
    また、C の構造体をそのまま `write` で送る方法もありますが、コンパイラによってすき間（パディング）の入り方が違うことがあるので、この教材のように 1 バイトずつ詰めるほうが安全です。
